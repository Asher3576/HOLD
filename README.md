# HOLD — 참은 것을 기록하는 투자 앱

> 수익률 대신, 계획대로 가고 있는지만 보여준다.
> 그리고 충동이 생기는 그 화면(남의 차트) 위로 직접 찾아간다.

---

## 1. 문제 정의

- 개인 투자자의 성과를 깎는 최대 요인은 전략이 아니라 **행동**이다: 감정에 의한 계획 외 매매, 잦은 차트 확인 → 스트레스 → 무리한 결정.
- 거래가 빈번할수록 수수료 구조로 계좌가 녹는다는 통계는 있지만, 자동매매가 수익을 낸다는 통계는 없다.
- AI로 전략을 생성·분석해도 결국 **인간이 개입**해서 계획을 깬다. 문제는 전략 부족이 아니라 **결정의 순간을 지켜주는 레이어의 부재**다.
- 그리고 그 "결정의 순간"은 우리 앱 안이 아니라 **증권사 화면과 차트 사이트에서** 일어난다. 앱만 만들면 충동의 현장에 없는 것이다. → 크롬 확장으로 현장에 간다 (9장).

## 2. 타겟 고객

- 매수는 하는데 "언제 팔지"에서 무너지는 개인 투자자.
- 하루에도 수십 번 계좌를 확인하며 스트레스 받는 사람.
- 계획(손절/익절)을 세워도 하락장이 오면 손절선을 옮기는 사람.

## 3. 가설

1. 수익률 숫자를 숨기고 **계획 대비 진행률**만 보여주면, 계획 외 매매가 줄어든다.
2. 매도 직전에 **본인의 과거 매도 기록**(판 뒤 올랐던 비율)을 비추면, 충동 매도가 줄어든다.
3. "참은 것"이 눈에 보이는 자산(열매)으로 쌓이면, 확인 중독이 수집 동기로 치환된다.
4. (확장) 진입 직전 **손익비와 본인 적중률**을 보면, 손익비 1 미만의 자리 진입이 줄어든다.

## 4. 검증 지표

- 계획 준수율: 원안(첫 계획) 그대로 끝까지 간 계획의 비율.
- 계획 이완 지수: 원안 대비 손절선·익절선·기간을 푼 정도(0~1). 하락 추세.
- 참은 기록의 사후 수익: hold_sell 열매의 outcome_pct 분포 — "참길 잘했다" 비율.
- 일일 금고 열람 횟수: 하락 추세.
- 반례 노출률: "어기고 벌었다" 케이스를 숨기지 않고 보여준 비율 100% 유지(정직성).
- (확장 퍼널) 확장 설치 → 손익비 점검 → "이대로 알 만들기" 전환율.
- (확장) 손익비 1 미만 자리에서 점검 후 알 생성을 접은 비율 — 코치가 일한 증거.

## 5. 해결 방식 — 결정 레이어

HOLD는 **실거래를 지원하지 않는다.** 주문 API도, 사용자 API 키도 없다.
사용자는 계획을 "알"로 만들고, HOLD는 그 계획이 끝까지 가도록 결정의 순간마다 개입한다.

### 5.1 핵심 기능 (앱)

| 기능 | 설명 |
|---|---|
| 수익률 숨김 | 손절가=0%, 익절가=100%로 놓은 **진행률**만 표시. 금액·수익률은 금고 안에. |
| 목표 근접 블러 | 진행률 80% 이상이면 숫자를 흐림 — goal-gradient(다 왔으니 팔자) 방어. |
| 매도 개입 | "팔고 싶다" 순간에 조언 대신 **본인 과거 매도 12건**의 30일 후 결과를 제시. 반례(팔길 잘한 건)도 반드시 함께. |
| 참은 기록(열매) | 개입 후 참으면 자동 저장. 시간이 지나면 결과가 채점되어 열매가 익는다. |
| 반사실(유령) 곡선 | 매도 기록만 제거한 "그때 안 팔았다면" 곡선. 실제 = 남은주식×현재가+회수현금, 유령 = 원수량×현재가. |
| 계획의 세 가지 끝 | 만기→재계약 or 완주, 손절선 작동→**보험이 일한 것**(실패 아님), 익절 완주→부화. |
| 논지 레이더 | 계획의 "이유"가 여전히 유효한지 관련 신호만 표시. 판단은 주지 않는다. |
| 말하는 복기 | 계획 종료 후 AI가 **질문만 하는** 대화형 복기. |

### 5.2 게이미피케이션 (홀디 세계관)

- **홀디**: 수호자 캐릭터(SVG). 표정 6종. **실망·비난 금지** — 놀람·보호·보고·축하만.
- **금고**: 계좌 요약은 다이얼 금고 안에. 열람할수록 다이얼이 오래 걸린다(1.5초 + 회차×0.4초).
- **알**: 계획 = 알. 품는 중 → 부화(완주) 도감 수집. 계획 없는 보유분은 "야생알".
- **열매**: 참은 기록. 채점되면 익는다.

## 6. 명시적 제약 (하지 않는 것)

1. **사용자 API 키를 절대 받지 않는다** — 유출 리스크 자체를 제거.
2. **실제 트레이딩 미지원** — 주문 실행 없음. 기록과 개입만.
3. **AI는 절대 사라/팔라를 말하지 않는다** — 자본시장법상 투자자문(수량·가격·시기 조언) 정의를 건드리지 않는다. 판단을 주지 않고, 판단을 비춘다. 확장의 브리핑·코치도 동일: **사실과 조건문만** ("저항 3번째 테스트, 거래량 감소. 이탈 시 다음 지지 63,800"), 지시어("사세요/파세요/진입하세요") 금지.
4. 시세는 **지연 시세** 사용 — 재배포 라이선스 리스크 회피. 실시간 호가 불필요.
5. (확장) **스크린샷 원본을 저장하지 않는다** — 캘리브레이션 처리 후 즉시 폐기. 페이지 DOM도 읽지 않는다.

## 7. 아키텍처

핵심 원칙: **수치는 서버가 결정적으로, LLM은 문장만.**

- `web/` — Vite + React 18 + TypeScript. 알·금고·도감·복기 앱.
- `extension/` — 크롬 확장 (Manifest V3). 오버레이·브리핑·손익비 코치. esbuild 번들.
- `shared/` — 순수 로직 패키지 `@hold/shared`: planMath(진행률·블러·이완지수), counterfactual(유령 계좌), rr(손익비·적중률). Vitest 테스트는 여기에.
- `supabase/` — Auth + Postgres + Edge Functions. 함수는 역할별 분리(단일 거대 파일 금지):
  - `ta/` — **결정적 계산 전용** (LLM 없음): 지지/저항 스윙, ADX/DMI, 손익비.
  - `vision/` — 스크린샷 → 축 캘리브레이션만. 원본 즉시 폐기.
  - `ai/` — **문장 생성 전용**: ta의 facts를 인용해 브리핑·복기 문장만 씀 (환각 방지).
  - `prices/` — 캔들 수집 크론 + 채점(열매·적중률).

## 8. 데이터 모델 요약

- 앱 코어: `plans`(알, 원안 필드 불변) · `plan_changes`(수정 이유 필수) · `held_records`(열매) · `reviews`(복기)
- 시세: `candles`(OHLCV — 스윙·ADX 계산에 고저가 필요해 종가 테이블 대체)
- 확장: `analyses`(브리핑/레벨/점검 기록 — facts+comment만, 스크린샷 없음) · `levels_cache`(심볼×타임프레임 20h 캐시) · `rr_checks`(손익비 점검, `linked_plan_id`로 알과 연결) · `calls`(방향 판단 이력 → 적중률, 채점 크론이 확정)
- 전 테이블 RLS. 시세·레벨 캐시는 읽기 전용(쓰기는 service role 크론만).

## 9. 크롬 확장 — 충동의 현장으로 간다

### 9.1 왜 확장인가

계획을 깨는 결정은 우리 앱이 아니라 **증권사 MTS/HTS 웹, 트레이딩뷰, 네이버 증권 화면에서** 일어난다. 확장은 HOLD를 그 현장에 세운다. 앱이 "금고"라면 확장은 **현장에 나가 있는 홀디**다.

퍼널: 확장(어느 차트에서든 만나는 간판·바이럴) → 손익비 점검 → "이대로 알 만들기" → 앱(리텐션·도감·복기).

### 9.2 기능 3+2

**① AI 애널리스트 — 간판·바이럴용**
어느 사이트든 지금 보는 차트에 즉석 브리핑: "65,200 저항 3번째 테스트, 거래량 감소 — 이탈 시 다음 지지 63,800". TA 수치는 서버가 결정적으로 계산하고 LLM은 문장만 쓴다(환각 방지). 봉 마감 라이브 코멘트는 Ext-3.

**② 지지/저항 오버레이 — ①의 심화, 데모 임팩트 최고**
레벨 계산은 스윙 로직, 비전은 Y축 라벨을 읽어 **가격↔픽셀 매핑에만** 사용 → 남의 차트 위 투명 레이어에 우리 선을 긋는다. 화면을 분석하는 척이 아니라, **자체 데이터로 계산한 레벨을 화면 좌표로 번역**하는 구조라 정확도가 화면 화질에 좌우되지 않는다.

**③ 손익비 코치 — 우리만의 해자**
진입·손절·목표 입력(또는 오버레이 드래그) → "손익비 1:2.3 · ADX 31 추세장 순방향 · 당신의 TSLA 상승 적중률 34%". **유저 본인의 판단 이력(calls)을 아는 도구는 우리뿐** — 일반 TA 확장이 절대 못 따라오는 부분. 점검 결과에서 바로 "이대로 알 만들기" → 앱 전환.

**④ 홀디 현장 개입**
보고 있는 심볼이 **내 알(active plan)이면** 홀디가 화면 구석에 나타난다: 익절 근처면 손으로 눈을 가리고(블러 정신의 현장판), "팔고 싶다"를 누르면 과거 매도 기록 카드를 현장에서 바로 보여준다(매도 개입의 현장판). 앱 기능이 확장에서 완성된다.

**⑤ 확인 중독 미터**
같은 차트를 오늘 몇 번 열었는지 확장이 센다(로컬 카운트, 서버 전송은 집계값만). "오늘 이 차트 14번째예요"를 홀디가 **비난 없이** 알려주고, 금고 열람 마찰과 같은 원리로 연결. 가설 검증 지표(확인 횟수 하락)의 측정 장치이기도 하다.

### 9.3 구현 가능성 평가

| 요소 | 난이도 | 평가 |
|---|---|---|
| 오버레이 그리기 | 쉬움 | `position:fixed` + `pointer-events:none` 레이어. 드래그 핸들만 이벤트 활성. 확실히 됨. |
| 화면 캡처 | 쉬움 | `activeTab` + `captureVisibleTab` — 클릭한 탭만, 그 순간만. 상시 권한 불필요. |
| 심볼 인식 | 중간 | **1순위 URL/타이틀 파싱** — 트레이딩뷰·네이버 증권 등 주요 사이트는 URL에 심볼이 있음(사이트 어댑터). 비전은 폴백, 최후엔 수동 입력 1회 후 사이트별 기억. |
| 서버 TA 계산 | 중간 | 스윙·ADX·손익비 모두 검증된 로직 포팅. 자체 캔들 필요 — 미국주식 Tiingo 확보됨, 국내주식 일봉 소스는 별도 확보 필요. |
| 비전 캘리브레이션 | 중간~어려움 | Y축 라벨 2점이면 선형 매핑 성립. 리스크: 로그 스케일(라벨 3개 이상으로 감지), 기기 배율(DPR 나눗셈), 줌/스크롤 시 재보정(쓰로틀 재캡처). **Ext-1은 수동 보정으로 시작**해 리스크를 우회하고, Ext-2에서 자동화. |
| 봉 마감 라이브 코멘트 | 어려움 | 분봉 실시간 데이터 비용·라이선스가 관건. 지연시세 원칙과 충돌 여지 → 후순위(Ext-3), 일봉 마감 코멘트부터. |

결론: **①②③은 구현 가능.** 가장 불확실한 비전 캘리브레이션은 수동 보정 폴백이 있어 출시 차단 요인이 아니다. ①의 "봉마다 라이브"만 후순위.

### 9.4 가드레일 (규제·프라이버시·심사)

- **표현**: 지시어 금지 — 사실·조건문만. LLM 출력에 컴플라이언스 필터 적용. 불특정 다수 대상 자동 분석이라도 개별 종목 매매 지시로 읽히는 문장은 차단. 유사투자자문업 신고 요건은 실서비스 전 법률 검토 1회.
- **프라이버시**: 스크린샷은 캘리브레이션 후 즉시 폐기(저장·로깅 금지 — 화면에 계좌 잔고가 찍혀 있을 수 있다). 비전 프롬프트에 "축 라벨 외 무시" 명시. `analyses`에는 host만 저장, URL 전체 저장 안 함. DOM 스크래핑 없음.
- **웹스토어 심사**: 상시 주입 없음(`activeTab`, 클릭 시에만) + 개인정보처리방침에 캡처 즉시 폐기 명시 → 금융 페이지 캡처 확장의 심사 리스크를 최소화.

## 시작하기

```bash
git clone https://github.com/Asher3576/HOLD.git
cd HOLD
pnpm install
pnpm dev        # 웹앱 — http://localhost:5173
```

`web/.env`에 Supabase 퍼블리셔블 키가 들어 있다(공개 안전 키라 커밋됨).
**시크릿 키(secret / service_role)는 절대 `.env`나 `VITE_` 변수에 넣지 말 것** — Vite는 `VITE_` 접두사 변수를 브라우저 번들에 그대로 노출한다.

## 명령어 (루트에서)

```bash
pnpm dev        # 웹앱 개발 서버
pnpm test       # 전 패키지 테스트 (Vitest)
pnpm typecheck  # 전 패키지 타입 체크
pnpm build      # 전 패키지 빌드 (확장은 extension/dist/)
```

크롬 확장 로드 방법은 [extension/README.md](extension/README.md) 참고.

```
    └── rr.ts                # 손익비·적중률 (확장 코치의 핵심)
supabase/
├── migrations/              # 스키마 (Phase B에서 적용) — 앱 + 확장 테이블
└── functions/
    ├── ta/                  # 결정적 TA: 스윙 레벨·ADX·손익비 (LLM 없음)
    ├── vision/              # 스크린샷 → 축 캘리브레이션만 (원본 즉시 폐기)

```

## 단계

- **Phase A (현재)**: 앱 UI 본구현 — 홀디·금고·알 선반 (목데이터).
- **Phase B**: Supabase 연결 — `supabase link --project-ref xpjtgmckrazfbyghkeve` 후 `supabase db push`, Auth 연동.
- **Phase C**: AI 복기·논지 레이더 + 시세 크론 + 채점.
- **Ext-1**: 오버레이+브리핑 (심볼 URL 파싱, 수동 보정) · **Ext-2**: 비전 캘리브레이션 · **Ext-3**: 라이브 코멘트.

## 원칙

- 사용자 API 키를 받지 않는다. 실거래를 지원하지 않는다.
- AI는 절대 사라/팔라를 말하지 않는다 — 수치는 서버가 결정적으로, LLM은 문장만.
- 스크린샷 원본은 저장하지 않는다. DOM을 읽지 않는다. 상시 주입하지 않는다.
- 홀디는 사용자를 혼내지 않는다 (실망·비난 표정 금지).
